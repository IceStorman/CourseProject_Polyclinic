# Етап 4. OLAP-куб (SQL Server Analysis Services)

## 4.1 Проєкт SSAS

| Параметр | Значення |
|---|---|
| Сервер | SQL Server Analysis Services 2022, режим **Multidimensional** (`localhost`) |
| База SSAS | `PolyclinicOLAP` (мова — українська 1058, колація `Ukrainian_CI_AS`) |
| Куб | `Поліклініка` |
| Проєкт Visual Studio | `SSAS_Projects/PolyclinicOLAP.sln` → `PolyclinicOLAP.dwproj` (Analysis Services Multidimensional Project) |
| Джерело даних | `PolyclinicDW` (OLE DB, MSOLEDBSQL); обробка від імені облікового запису служби SSAS (`ImpersonateServiceAccount`) |

**Структура `SSAS_Projects/`:**

```
SSAS_Projects/
├── PolyclinicOLAP.sln              — рішення Visual Studio
├── PolyclinicOLAP/                 — проєкт: .ds, .dsv, 9 × .dim, .cube, .partitions, .dwproj
├── Builder/                        — створення, розгортання та обробка куба (C#, AMO)

│   ├── MdxScript.cs                — MDX-скрипт (обчислювані міри, набори)
│   ├── Kpis.cs                     — KPI
│   ├── ProjectExporter.cs          — експорт розгорнутої бази у проєкт Visual Studio
│   ├── GRANT_SSAS_ACCESS.sql       — доступ служби SSAS до сховища
│   └── build_cube.ps1              — повна збірка: розгортання → ProcessFull → агрегації → резервна копія
└── Tests/
    ├── mdx/*.mdx                   — 9 демонстраційних MDX-запитів
    ├── run_mdx.ps1, run_all_mdx.ps1 — виконання запитів (результати: mdx_results.txt)
```

Розгорнута база експортується у звичайний проєкт Visual Studio, який відкривається в дизайнері
та збирається без помилок.

## 4.3 Виміри (9)

| Вимір | Ключ (Name Column) | Атрибути | Ієрархії |
|---|---|---|---|
| **Дата** (Time) | DateKey (DateName) | Рік, Півріччя, Квартал, Місяць, Місяць року, День тижня, Сезон, Тип дня | **Календар:** Рік → Півріччя → Квартал → Місяць → Дата |
| **Пацієнт** (SCD2) | PatientKey (FullName) | Місто, Регіон, Група міст, Стать, Рік народження, Група крові, Страховка, Поточна вікова група, Код пацієнта (властивість члена) | **Географія:** Регіон → Місто → Пацієнт |

| **Хвороба** | DiseaseKey (DiseaseFullName) | Клас МКХ-10, Перебіг, Тяжкість, Інфекційність, Сезонність | **Класифікація МКХ-10:** Клас → Хвороба |

| **Вікова група** | AgeGroupKey | Вікова категорія | **Вік:** Категорія → Група |
| **Тип візиту** | VisitTypeKey (VisitTypeLabel) | Тип візиту, Статус візиту | **Тип → статус** |
| **Результат лікування** | OutcomeKey | Група результату | **Результати:** Група → Результат |
| **Аналіз** | LabTestKey | Група аналізів | **Аналізи:** Група → Аналіз |

Вимоги до вимірів:
- **Key Attributes.** Сурогатні ключі сховища. Для складених ключів (Місяць = Рік + № місяця,
  Квартал = Рік + № кварталу) задано окрему колонку назви.
- **Attribute Relationships.** Задано для всіх ієрархій. Для календаря зв'язки **Rigid**:
  Дата → Місяць → Квартал → Півріччя → Рік; Дата → День тижня; Місяць → Місяць року → Сезон.
  Для атрибутів SCD2 (місто, категорія лікаря) — **Flexible**.
- **Name Column та Order By.** Назви беруться з окремих колонок (назва місяця, квартал з роком);
  сортування — за ключем (місяці в календарному, а не алфавітному порядку).
- **SCD Type 2.** У вимірах «Пацієнт» і «Лікар» ключ — сурогатний ключ версії. Тому факти
  прив'язані до версії, чинної на момент події: візит до переїзду рахується за старим містом.
- **Типи атрибутів часу** (Years, HalfYears, Quarters, Months, Date, DayOfWeek, MonthOfYear)
  потрібні для функцій Time Intelligence.
- **Невідомі члени.** Таблиці вимірів мають власний рядок «Невідомо» (ключ −1), тому системний
  Unknown Member вимкнено. `KeyDuplicate = ReportAndStop`: суперечливі атрибути (наприклад,
  одне місто у двох регіонах) зупиняють обробку. Обробка проходить без помилок.
- **Рольовий вимір.** Вимір «Дата» використовується двічі: **Дата** (дата візиту, призначення,
  аналізу або закриття історії хвороби) і **Дата відкриття історії** (лише для групи «Лікування»).

## 4.5 MDX-обчислення

Повний текст — `SSAS_Projects/Builder/MdxScript.cs` і вкладка Calculations куба в Visual Studio.

| Категорія | Обчислювані міри та набори |
|---|---|
| **Відсоткові** | Рівень одужання, Ефективність лікування, Дотримання нормативу, Частка неявок, Частка аналізів з відхиленням, **Частка виручки** (% від загальної, через `Root()`) |
| **Time Intelligence** | **Виручка YTD** (`YTD`), **Виручка PY** і **Візити PY** (`ParallelPeriod`), **Ріст виручки YoY**, **Ріст візитів YoY**, **Ріст візитів MoM** (`PrevMember` на рівні місяця) |
| **Ковзне середнє** | Ковзне середнє візитів (3 періоди), Ковзне середнє виручки (12 місяців) — `AVG(LastPeriods(n, ...))` |
| **Рейтинги** | Набори **Топ-10 лікарів за виручкою**, **Топ-10 хвороб за випадками**, **Топ-10 препаратів за вартістю** (`TOPCOUNT`); міри **Рейтинг лікаря за виручкою**, **Рейтинг хвороби за випадками** (`RANK` + `ORDER`) |
| **Бізнес-показники** | Виручка на годину прийому, Вартість лікування на випадок, Перевищення нормативу (днів), Ліки на один візит, Середня вартість візиту, Середня тривалість лікування, Візитів на пацієнта |

Приклад (ріст виручки рік до року):

```mdx
CREATE MEMBER CURRENTCUBE.[Measures].[Виручка PY] AS
    ([Measures].[Виручка], ParallelPeriod([Дата].[Календар].[Рік], 1, [Дата].[Календар].CurrentMember)),
    FORMAT_STRING = "#,##0.00", DISPLAY_FOLDER = 'Динаміка', ASSOCIATED_MEASURE_GROUP = 'Візити';

CREATE MEMBER CURRENTCUBE.[Measures].[Ріст виручки YoY] AS
    IIF(ISEMPTY([Measures].[Виручка PY]) OR [Measures].[Виручка PY] = 0, NULL,
        ([Measures].[Виручка] - [Measures].[Виручка PY]) / [Measures].[Виручка PY]),
    FORMAT_STRING = "Percent", DISPLAY_FOLDER = 'Динаміка', ASSOCIATED_MEASURE_GROUP = 'Візити';
```

### KPI (4)

| KPI | Значення | Ціль | Статус (світлофор) | Тренд |
|---|---|---|---|---|
| Ефективність лікування | Ефективність лікування | 80% | ≥ 80% → 1; ≥ 75% → 0; інакше −1 | порівняння з попереднім роком |
| Дотримання нормативу лікування | Дотримання нормативу | 60% | ≥ 60% → 1; ≥ 50% → 0; інакше −1 | порівняння з попереднім роком |
| Частка неявок | Частка неявок | ≤ 4% | ≤ 4% → 1; ≤ 6% → 0; інакше −1 | менше — краще |
| Ріст виручки | Ріст виручки YoY | +5% | ≥ 5% → 1; ≥ 0 → 0; інакше −1 | порівняння з попереднім роком |

## 4.6 Налаштування та оптимізація

**Режими зберігання (Storage Mode):**

| Група мір | Режим | Обґрунтування |
|---|---|---|
| Візити, Унікальні пацієнти, Призначення, Лікування | **MOLAP** | Основні дані для звітів: найшвидші запити, дані стиснуті в кубі |
| Аналізи | **HOLAP** | Агрегати в кубі, детальні рядки читаються зі сховища. Невеликий обсяг, деталізація потрібна рідко |
| Виміри | MOLAP | — |

**Партиції.** Великі групи мір поділено за роками (query binding з умовою
`DateKey BETWEEN yyyy0101 AND yyyy1231` і `Slice` на рік):
- «Візити» — 11 партицій (2016–2026, ≈ 77–132 тис. рядків кожна);
- «Призначення» — 11 партицій.

Обробляти можна лише партицію поточного року (ProcessFull / ProcessData), не чіпаючи історію.

**Дизайн агрегацій** (Aggregation Design Wizard, ціль — 30% приросту продуктивності):

| Група мір | Агрегацій | Оцінка оптимізації |
|---|---:|---:|
| Візити | 55 | 30% |
| Унікальні пацієнти | 56 | 30% |
| Лікування | 14 | 31% |
| Аналізи | 4 | 32% |
| Призначення | 46 + 5 ручних | 26% (максимум алгоритму) |

Для групи «Призначення» алгоритм завершує роботу на 26%: решта кандидатів перевищують
допустимий розмір агрегації. Тому додано 5 ручних агрегацій під типові запити звітів:
- фармгрупа × місяць;
- препарат × місяць;
- спеціальність × місяць;
- клас МКХ-10 × місяць;
- препарат × вікова категорія × рік.

Атрибути з великою кількістю членів (окремі пацієнти) виключено з агрегацій
(`AggregationUsage = None`), а місяць включено в усі агрегації (`Full`).

**Оптимізація атрибутних зв'язків:**
- зв'язки Rigid для календаря;
- ланцюжки зв'язків замість «зірки» від ключа (Дата → Місяць → Квартал → Рік);
- атрибут «Код пацієнта» — лише властивість члена (`AttributeHierarchyEnabled = False`).

**Продуктивність: OLTP vs сховище vs OLAP** (`Tests/test_performance.ps1`; «холодний» запуск —
після очищення кешів, «теплий» — середнє 3 повторів):

| Запит | Холодний, мс | Теплий, мс |
|---|---:|---:|
| Q1 візити/виручка/пацієнти за роками × спеціальностями — OLTP | 197 | 96 |
| Q1 — сховище (зірка) | 167 | 70 |
| Q1 — **OLAP-куб** | 105 | **5** |
| Q2 статистика захворювань: клас × рік × вікова група — OLTP | 6 385 | 6 257 |
| Q2 — сховище (зірка) | 136 | 26 |
| Q2 — **OLAP-куб** | 36 | **18** |
| Q1 — OLAP без агрегацій | 102 | 5 |
| Q2 — OLAP без агрегацій | 35 | 18 |

Висновки:
- Аналітичний запит Q2 до OLTP-бази виконується понад 6 с: потрібні з'єднання 5 таблиць і
  обчислення віку для 535 тис. історій. До куба той самий запит виконується за **36 мс
  (у ~175 разів швидше)**. Зіркова схема сховища вже дає прискорення в ~47 разів.
- При обсязі ~1 млн рядків у групі мір вплив агрегацій незначний: MOLAP-партиції стиснуті й
  скануються за мілісекунди. Агрегації дають помітний ефект на десятках і сотнях мільйонів
  рядків. Дизайн агрегацій підготовлено для зростання обсягів.

**Попередження Visual Studio (Best Practices)**, залишені свідомо:
- *Avoid visible attribute hierarchies for levels*: атрибути (Рік, Спеціальність, Клас
  МКХ-10) залишено видимими, бо вони потрібні як окремі осі у звітах SSRS і зведених таблицях;
- *Consolidate partitions*: партиції за роками є вимогою завдання й демонструють обробку окремих років;
- *Unsupported OLE DB provider*: використовується актуальний провайдер MSOLEDBSQL
  (SQLNCLI застарів); обробка проходить успішно.
